# 開発

```sh
npm ci
npm run dev        # http://localhost:5173/
npm run typecheck  # 型チェック
npm run check      # Biome（lint・整形。Markdown と YAML も見る）
npm test           # テスト
npm run build      # out/ に出力（公開先に合わせて base は /joseniq/）
```

作りは [architecture.md](architecture.md)、守る決まりは [design.md](design.md) に書いてある。

## ブランチとリリース

- 作業は develop から切ったブランチで行い、develop へ PR を出す。develop に入ると GitHub Pages に公開される
- 毎朝6時（日本時間）に develop から master への PR が自動で出る。含まれる Issue に enhancement があれば `bump:minor`、なければ `bump:patch` のラベルが付き、package.json の版が上がる
- master に入ると、その版でタグとリリースが作られる
- 版を上げるワークフロー（bump-version.yml）は README.md もコミットに含めるので、README.md は消さない（ないと版上げが失敗する）

## PR を出す前に

- `npm run typecheck`・`npm run check`・`npm test` を通す。`npm run check` は Markdown と YAML も見るので、文書やワークフローだけを変えたときも走らせる
- 動きや決まりを変える PR では、関係する docs（design.md・architecture.md・この文書）と README.md も同じ PR で直す

## 数値の調整に使うスクリプト

どちらもテストではないので、結果で失敗にはしない。戦いは `src/sim/` の `runPlan` で、画面を使わずに最後まで回す。

| コマンド                 | 何を出すか                                                                                                                                                                | 使いどころ                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `npm run balance`        | 「基本（平城）」の城に、編成例5種を出撃口8か所から当てた結果の表（勝ちなら落城までの時間、負けなら本丸の残りの体力）                                                      | 数値や仕組みを変えたあと、勝ちやすさがどう変わったかを見る。武将の新しい特徴が、その武将のいない戦いを変えていないかを比べる |
| `npm run balance:combos` | 武将3人の組み合わせ（7人から3人の35通り）を、編成例と出撃口に当てた勝率。比べるための「武将なし」、武将ごと・編成例ごと・出撃口ごとのまとめ、上位と下位、勝率の分布も出す | 武将どうしの釣り合いの実績を集める。`npm run balance:combos -- --out ファイル名` で、1戦ずつの結果を JSON に書き出す         |

`runPlan` は、画面と違い、予定を出し切って攻め手がいなくなった時点で全滅にする（[architecture.md](architecture.md) の「戦いの計算の流れ」）。数値は今は仮で、結果からすぐに数値を直すことはしない（[design.md](design.md) の「数値は仮」）。

## 画面の確かめ方

### 開発サーバーが古いコードを返すとき

WSL の上では、`npm run dev` の開発サーバーが、ファイルを変えても古いコードを返し続けることがある。画面で確かめる前に、開発サーバーを立ち上げ直すか、`curl http://localhost:5173/src/ui/app.ts` などで新しいコードが返るかを見る（Vite は書き直して返すので、引用符などが変わっていることがある）。

### ヘッドレスブラウザ（Playwright）で確かめるとき

- プロジェクトには Playwright を入れていない。使うときは、別の場所に `playwright-core` を入れて、そこからスクリプトを動かす（ブラウザの版と合わせる）
- 5173 番で別の開発サーバーが動いていることがあるので、別の番号（`npx vite --port 5180 --strictPort` など）で立ち上げる
- 施設の上を道具で押して 400ms 動かさないと、長押しでその施設をつかむ。ヘッドレスでは描画が重く、1歩に数百 ms かかることがあるので、なぞる操作は押した直後に 8px より大きく動かす
- 盤面でつかんでいるかは、`#cv` の `style.cursor` が `grabbing` かで分かる
- 盤面は3Dの斜め見下ろしなので、決まったマスを押すには、開発サーバーでだけ使える `window.joseniq` を使う（`npm run build` の版には入らない）
  - `joseniq.tileToClient(x, y)`：マス (x, y) の中心が見えている位置 `{ x, y }`。`clientX`・`clientY` と同じく、見えている範囲の左上からの位置なので、`page.mouse.click` にそのまま渡せる。スクロールなどで見えている範囲の外にあるときは `null`（`#cv` を見える所までスクロールしてから求め直す）
  - `joseniq.tileAt(clientX, clientY)`：その位置に見えているマス（盤面の外なら `null`）。押す前に、`tileToClient` で求めた位置が狙ったマスかをこれで確かめる
  - 建物や高い段の陰に隠れたマスは、隣のマスが返る。視点を回してから求め直す
  - `joseniq.deploys()`：今の戦いで出撃した記録（ティック・兵種・マス）。予定どおりに出たかを確かめるのに使う
  - 攻城の開戦前は、口の目印が `#gatePins .gatePin`（口の番号の順）、軍評定の窓が `#council` にある
  - 求めた位置は、そのときの視点と盤面のもの。視点を動かした直後（「向きを戻す」など）は少し待ってから求める。開戦後は駒が動いて重なりが変わるので、一時停止してから求めて押す

## 1対1の戦いの確かめ

`duel.html`（開発サーバーの `/duel.html`）は、兵・武将・施設の1対1の戦いを目で見て確かめるページ。どの時刻にどれだけ傷が入り、いつ勝負がつくかを見る。ゲームの画面からはリンクしない。

- 左はいつも攻め手（兵か武将）、右は守り（武将か施設）。武将どうしのときは「左右を入れ替える」で攻守を逆にできる。盤面は平地だけ
- 戦いの計算はふだんの `step` をそのまま使う。守りの武将の `aggro`・`leash` もふだんの値のままなので、距離によって、動き出す時刻や最初に当てる側が変わる。武将は `pref` のとおりに動くので、たとえば施設を好む武将は守将を追わず、近づいたときだけ相手にする
- 本丸は戦いに関わらないよう、右の相手の後ろに置き、体力を大きくしている。兵は本丸への道の途中で相手へ寄り道するため、本丸を消すと動かない。相手を攻撃しない組み合わせは、時間切れで決着なしになる
- 1対1なので、体力の減った分は相手が与えた傷として一覧に出す
- 数値を試すときは `src/sim/defs.ts` を直す。ページが読み直されても、選んだ組み合わせと距離は URL に残る。武将の能力値は攻守で同じにする決まり（`docs/design.md`）はここでも守る
- 開発サーバーでだけ、`window.duelPage.duel()` で今の戦いを読める

## 武将の大きな絵を作り直す

大きな絵（`docs/design.md` の「武将と兵の大きな絵」）は、`scripts/sprites/` のスクリプトで作る。ゲームが読むデータ（`src/ui/` の `*Frames.ts`。武将7人と、描き直した兵の1種ごとに1つずつ）は書き出したものなので、手で直さない。兵も同じ作り方で描く。

| ファイル               | 中身                                                                                                                                                                                                                                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `common.js`            | 素材ごとの色（暗・影・地・明の4段）、外側の輪郭の色、多角形の内外の判定                                                                                                                                                                                                                 |
| `kenshin.js` など7人分 | 武将ごとの描き方（`kenshin.js`・`nobunaga.js`・`mitsuyoshi.js`・`masayuki.js`・`hideyoshi.js`・`ieyasu.js`・`shingen.js`）。頭は手で置いた絵（`HEAD_FRONT`・`HEAD_BACK`）、体は多角形・楕円・線と、膝と肘の曲げで組み、コマごとの姿勢（傾き・沈み・踏み込み・武器の位置と向き）を並べる |
| `ashigaru.js`          | 兵の7種の描き方。共通の作り（`mkTroop`）に、頭・持ち物・胴の有無・馬・車と各コマの姿勢を兵ごとに渡す。作りは武将と同じで、武将の半分ほどの大きさ（背丈20ドットほど）に簡単に描き、56×48 の枠に切り出す。兵は幟を持たない                                                                |
| `export.mjs`           | 全コマとコマごとの幟の位置を書き出す                                                                                                                                                                                                                                                    |
- 書き出し：`node scripts/sprites/export.mjs kenshin`（信長は `nobunaga`、光義は `mitsuyoshi`、昌幸は `masayuki`、秀吉は `hideyoshi`、家康は `ieyasu`、信玄は `shingen`、歩兵は `ashigaru`、弓兵は `yumi`、騎兵は `kiba`、衝車は `shosha`、工兵は `kouhei`、盾兵は `tate`、斥候は `monomi`）。書き出したあと Biome で整える
- 書き出しの色は、1つの絵につき52色まで（色を表す文字が英字だけで、数字は続く数に使うため）。超えると `export.mjs` が止まる。色を足すときは、今ある色で描けないかを先に考える
- `common.js` と描き方のファイルは、つなげて読む前提で互いの名前を使うので、Biome のチェックから外している（`biome.json`）
- 武将と兵のモーションの確かめのページ（`motion.html`・`src/motion.ts`）：大きな絵の武将と兵を並べて再生し、コマの長さ・速さごとの実際の長さ・能力値を図と表にする。開発サーバーなら `http://localhost:5173/motion.html`、公開の版なら `/joseniq/motion.html` で開く。ゲームの画面からはリンクしていない
  - 絵・コマの選び方（`src/ui/bigBusho.ts` の `bigFrame`）・攻撃の区切り（`ATTACK_TIME`）・能力値（攻めの表 `ADEF`。武将の値は攻守で同じ）は、ゲームと同じものを読む。どの駒も同じ大きさの枠に足元をそろえて描くので、武将と兵の大きさの違いがそのまま見える。ゲームの側を変えれば、ページもそのまま変わる
  - 「戦い始め」は、歩いて敵の前に着いてから続けて攻撃するまでを出す。どの駒も着いたその時に1回目を攻撃する。スキルを持つ武将は、1回目の番でスキルを出す
  - スキルは、動きの切り替えの「攻撃」の隣に置く。選ぶと、スキルを持つ武将だけを出し、スキルを続けて出す形でくり返す（試作の時間を持たないので、いつもゲームの時間）。コマの長さの図と速さごとの表も、スキルを持つ武将だけの段にする。戦い始めでは、スキルを持つ武将の段の中に1回目のスキルが入る。スキルのコマの名前には「スキル：」を付ける
- スキルのコマは、描き方のファイルの各向きに `スキル`（攻撃と同じく名前と絵の組の5つ）を持たせると、`export.mjs` が `skill` として書き出す。持たせなければ書き出さない（今は家康・謙信・光義・信長）。区切りは `SKILL_TIME`、ページのコマの名前は `src/motion.ts` の `BARE_SKILL` に、武将ごとに足す
  - 開発サーバーでだけ、`window.motionPage.seek(秒)` で、戦闘の秒を決めて止められる（ヘッドレスブラウザで決まったコマを撮るため）
- 武将を足すときは、描き方のファイルを足し、`export.mjs` の `CONF` に1行足す。書き出したデータは `src/ui/bigBusho.ts` の `BIG` に入れる。`BIG` は全員分を求める表で、盤面と確かめのページの両方が読むので、ブランチの上で確かめのページを見せ、ユーザーの確認を得てからマージする。幟の家紋は `pixel.ts` の表（`bushoMon`）から取る
- 幟を立てる位置は、描き方の側がコマに頭の上の端（`top`）を持たせればそれを使う（光義・昌幸・秀吉・家康・信玄）。持たせなければ、`export.mjs` が色から求める（謙信は頭巾、信長は元結）
- 兵（`CONF` に `troop: true`）は幟を書き出さず、待機のコマの頭の上の端（`top`）を書き出す。体力の棒はその上に出す。兵の描き方は、コマに `top` を持たせる
- 武器ごとの攻撃の区切りは `ATTACK_TIME`（刀・槍・鉄砲・弓・軍配の采配・軍配で打つ・槌・盾で押す・手を振る・衝車の丸太）。離れた所を指す軍配の武将（昌幸・信玄）は采配の区切りを、近くを打つ家康は軍配で打つ区切りを使う。衝車は丸太、持ち物のない斥候は手を振る区切りを使う（`bigWeapon`）。新しい武器を足すときは、区切りと、ページの攻撃のコマの名前（`src/motion.ts` の `ATTACK_NAMES`）を足す
